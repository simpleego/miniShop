# 장바구니와 재고 관리 — 여러 사용자가 동시에 같은 상품에 접근할 때

> **질문** : 쇼핑몰에서 장바구니 기능을 구현할 때, 여러 사용자가 동시에 하나의 상품에 접근한다고 가정하고 재고 관리를 해야 하는가?
>
> **결론** : **장바구니 단계에서는 재고를 잡아두지 않고 확인만 한다.**
> **동시 접근을 고려한 재고 관리는 주문(결제) 단계에서 한다.**

---

## 1. 왜 장바구니에서 재고를 빼지 않나?

| 장바구니에 담을 때 재고를 빼면 | 문제 |
|------------------------------|------|
| 사용자는 장바구니에 담고 사지 않는 경우가 훨씬 많다 | 실제로는 팔리지 않을 상품의 재고가 묶인다 |
| 담아 두고 며칠씩 방치한다 | 다른 사람에게는 "품절"로 보여서 못 산다 |
| 악의적으로 대량으로 담는다 | 재고를 막아 버리는 공격이 가능하다 |

그래서 일반 쇼핑몰은 다음처럼 나눠서 처리한다.

| 단계 | 재고 처리 | 정확도 |
|------|----------|--------|
| 장바구니 담기 | 화면 안내용으로 **확인만** ("재고 3개 남음") | 대략 맞으면 된다 |
| 주문 화면 진입 | 서버에 **최신 재고 다시 확인** | 대략 맞으면 된다 |
| **결제(주문 확정)** | **DB 에서 재고를 실제로 차감.** 동시성 제어 필요 | **반드시 정확해야 한다** |

userstory 문서의 프론트 코드에서 `inCart >= product.stock` 으로 확인하는 것도 **안내용**일 뿐이다.
장바구니에 저장된 `stock` 은 담을 때의 값이고, 사용자가 브라우저에서 얼마든지 바꿀 수 있기 때문에
**최종 판단은 반드시 서버가 해야 한다.**

---

## 2. 동시에 주문하면 무슨 일이 생기나?

재고 1개인 콜라를 A, B 가 동시에 결제한다고 하자. 흔히 쓰는 "읽고 → 확인하고 → 쓰는" 방식은 이렇게 된다.

```
시간   사용자 A                           사용자 B
 1    SELECT stock → 1
 2                                       SELECT stock → 1
 3    1 >= 1 이니까 OK
 4                                       1 >= 1 이니까 OK
 5    UPDATE stock = 0
 6                                       UPDATE stock = 0
결과   재고 1개인데 2명에게 판매됨 ❌ (초과 판매)
```

재고가 5개일 때도 비슷하다. 두 사람이 모두 5를 읽고 `stock = 4` 로 쓰면,
**2개가 팔렸는데 재고는 1개만 줄어드는** 문제가 생긴다. (Lost Update, 갱신 손실)

> 이 프로젝트의 `products` 테이블에는 `CHECK (stock >= 0)` 제약이 있어서 재고가 음수가 되는 것은 DB 가 막아 준다.
> 하지만 위처럼 계산한 값을 그대로 쓰는 경우는 막지 못하므로, **마지막 안전장치**로만 생각해야 한다.

## 3. 해결 방법 (주문 API 에서)

### 방법 ① 조건부 UPDATE 한 줄 (가장 간단, 추천)

확인과 차감을 **SQL 한 문장**으로 처리한다. DB 는 이 한 문장을 다른 요청과 섞이지 않게 처리한다.

```sql
UPDATE products
SET stock = stock - %s            -- 읽은 값이 아니라 현재 DB 값에서 뺀다
WHERE id = %s AND stock >= %s     -- 재고가 충분할 때만
```

```python
with conn.cursor() as cursor:
    affected = cursor.execute(sql, (quantity, product_id, quantity))
    if affected == 0:
        # 바뀐 행이 없음 = 재고 부족 (그 사이 다른 사람이 사 갔음)
        raise HTTPException(status_code=409, detail="재고가 부족합니다.")
```

위 예시에 적용하면 A 가 먼저 성공해서 재고가 0 이 된다.
B 의 UPDATE 는 `stock >= 1` 조건에 맞지 않아 **0행이 바뀌고**, B 는 "재고 부족" 응답을 받는다.

### 방법 ② 비관적 락 (`SELECT ... FOR UPDATE`)

여러 상품을 한 번에 주문하거나, 차감 전에 확인할 것이 많을 때 쓴다.

```sql
START TRANSACTION;
SELECT stock FROM products WHERE id = %s FOR UPDATE;   -- 이 행을 잠금 (다른 요청은 대기)
-- 재고 확인, 주문 저장(orders, order_items), 재고 차감 ...
COMMIT;                                                -- 잠금 해제
```

### 방법 ③ 낙관적 락 (version 컬럼)

충돌이 드물다고 보고 잠그지 않는 방식이다.
대신 저장할 때 `WHERE version = 읽은값` 조건으로 확인하고, 실패하면 다시 시도한다.

### 방법 비교

| 방법 | 장점 | 단점 | 언제 |
|------|------|------|------|
| ① 조건부 UPDATE | 간단하고 빠르다 | 복잡한 검증을 넣기 어렵다 | **대부분의 쇼핑몰 재고 차감** |
| ② FOR UPDATE | 확실하다 | 사람이 몰리면 대기가 길어진다 | 여러 테이블을 함께 바꾸는 주문 처리 |
| ③ 낙관적 락 | 잠금이 없다 | 충돌하면 재시도해야 한다 | 충돌이 드문 수정 작업 |

### 여러 상품을 한 번에 주문할 때 — 트랜잭션

장바구니에 콜라와 생수가 있을 때는 **트랜잭션**으로 묶어야 한다.
하나라도 재고가 부족하면 전부 취소(ROLLBACK)해야 콜라만 차감되는 일이 생기지 않는다.

```python
conn = get_connection()
try:
    with conn.cursor() as cursor:
        for item in items:
            affected = cursor.execute(sql, (item.quantity, item.product_id, item.quantity))
            if affected == 0:
                raise HTTPException(409, f"재고 부족: 상품 {item.product_id}")
        # orders, order_items INSERT ...
    conn.commit()        # 모두 성공 → 확정
except Exception:
    conn.rollback()      # 하나라도 실패 → 전부 취소
    raise
finally:
    conn.close()
```

> pymysql 은 기본값이 `autocommit=False` 라서 `commit()` 을 호출하기 전까지는 확정되지 않는다.

## 4. 예외 — 장바구니·주문 화면에서 재고를 잡아두는 경우

| 서비스 | 방식 |
|--------|------|
| 공연·항공권 예매, 한정판 판매 | 주문 화면에 들어가면 **N분 동안 재고 선점(예약)**, 시간이 지나면 자동 해제 |
| 선착순 이벤트 | Redis 같은 빠른 저장소로 재고를 먼저 차감하고 대기열 사용 |

일반 쇼핑몰이나 이번 자판기 프로젝트에는 필요 없는 수준이다.

---

## 5. 정리

- **장바구니** : 재고를 빼지 않고 **확인만** 한다. userstory 문서의 프론트 코드 방식으로 충분하다.
- **결제(주문)** : 동시성 제어가 **반드시** 필요하다.
  `UPDATE ... SET stock = stock - ? WHERE stock >= ?` 로 확인과 차감을 한 번에 하고, 여러 상품은 트랜잭션으로 묶는다.
- 프론트의 재고 확인은 **사용자 안내용**이고, **최종 판단은 서버와 DB 가 한다.**
