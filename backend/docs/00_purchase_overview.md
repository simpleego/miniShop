# 0. 구매하기 기능 개요

> 이 문서에서는 코드를 작성하지 않는다. **무엇을 어디까지 만들지** 먼저 정한다.

---

## 1. 구현 범위

| 단계 | 기능 | 포함 여부 |
|---|---|---|
| 필수 | 상품 1개를 수량을 정해 즉시 구매 | ✅ |
| 필수 | 구매 시 재고 차감, 품절이면 구매 불가 | ✅ |
| 필수 | 화면의 구매 버튼, 구매 후 재고 갱신 | ✅ |
| 권장 | 동시에 구매해도 초과 판매되지 않게 처리 | ✅ |
| 권장 | 내 주문 목록 / 주문 상세 조회 | ✅ |
| 심화 | 장바구니(여러 상품) 한 번에 주문, 주문 취소 | 과제 |
| 제외 | 실제 결제(PG), 쿠폰/포인트, 배송, 환불 | ❌ |

> **로그인은 아직 없다.** 그래서 주문자는 `user_id = 1` 로 **고정**한다.
> 나중에 로그인 기능을 만들면 "로그인한 사용자 id" 로 바꾸기만 하면 된다.

## 2. 사용하는 테이블

```
users (회원)
  │ 1
  │
  │ N
orders (주문 1건)                 ← 누가, 총 얼마, 상태(PAID/CANCELLED), 언제
  │ 1
  │
  │ N
order_items (주문 1건 안의 상품)   ← 어떤 상품을, 몇 개, 그때 가격 얼마
  │ N
  │
  │ 1
products (상품)                   ← 재고(stock)가 줄어든다
```

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `orders` | `id`, `user_id`, `total_price`, `status`, `created_at` | `status` 기본값 `'PAID'` |
| `order_items` | `id`, `order_id`, `product_id`, `quantity`, `unit_price` | `CHECK (quantity > 0)` |
| `products` | `id`, `name`, `price`, `stock`, `is_active` | `CHECK (stock >= 0)` |

### 왜 `order_items` 에 `unit_price` 를 따로 저장할까?

상품 가격은 나중에 바뀔 수 있다. 콜라를 1,500원에 샀는데 다음 달 1,700원으로 오르면,
`products.price` 만 보고 계산하면 **지난 주문 금액이 바뀌어 버린다.**
그래서 **구매 당시 가격**을 주문 상품에 복사해 둔다.

### 왜 주문을 테이블 2개로 나눌까?

주문 1건에 상품이 여러 개 들어갈 수 있기 때문이다 (장바구니 주문).
이번 필수 실습은 상품 1개만 사지만, 테이블은 처음부터 여러 개를 담을 수 있게 되어 있다.

## 3. API 설계

| 메서드 | 주소 | 설명 | 성공 코드 | 단계 |
|---|---|---|---|---|
| POST | `/orders` | 구매하기 (주문 생성) | 201 | 필수 |
| GET | `/orders` | 내 주문 목록 | 200 | 권장 |
| GET | `/orders/{order_id}` | 주문 상세 (주문 상품 포함) | 200 | 권장 |
| POST | `/orders/{order_id}/cancel` | 주문 취소 | 200 | 심화 |

### 구매 요청 / 응답

```http
POST /orders
Content-Type: application/json

{ "product_id": 1, "quantity": 2 }
```

```json
// 201 Created
{
  "order_id": 17,
  "product_id": 1,
  "product_name": "콜라",
  "quantity": 2,
  "unit_price": 1500,
  "total_price": 3000,
  "status": "PAID"
}
```

> ⚠️ 요청에 **가격(price)이 없다.** 의도한 설계다.
> 가격을 클라이언트가 보내게 하면, 개발자 도구로 `"price": 1` 로 바꿔 1원에 살 수 있다.

### 실패 응답

| 상황 | 상태코드 | `detail` 예시 |
|---|---|---|
| `quantity` 가 0 이하, 숫자가 아님, 필드 누락 | 422 | (FastAPI 자동 응답) |
| 상품이 없거나 판매중지(`is_active = 0`) | 404 | `상품을 찾을 수 없습니다.` |
| 재고가 부족함 | 409 | `재고가 부족합니다. (남은 재고: 1개)` |
| DB 오류 등 예상하지 못한 문제 | 500 | `주문 처리 중 오류가 발생했습니다.` |

> **409 Conflict** : "요청 형식은 맞지만 지금 서버 상태(재고)와 충돌해서 처리할 수 없다" 는 뜻이다.
> 400 을 써도 틀린 건 아니지만, 입력 오류(422)와 구분하려고 409 를 쓴다.

## 4. 구매 처리 흐름

```
[프론트] 구매 버튼 클릭
   │  POST /orders { product_id, quantity }
   ▼
[서버] ① 입력 검증 (Pydantic)              실패 → 422
   │
   ▼
   ② 상품 조회 (판매중인 상품인지)          없음 → 404
   │
   ▼
   ③ 재고 확인                              부족 → 409
   │
   ▼
 ┌─────────── 트랜잭션 (하나로 묶음) ───────────┐
 │ ④ orders INSERT       → 새 주문 번호 얻기     │
 │ ⑤ order_items INSERT  → 구매 당시 가격 저장   │
 │ ⑥ products UPDATE     → 재고 차감             │
 └──────────────────────────────────────────────┘
   │  모두 성공 → COMMIT  /  하나라도 실패 → ROLLBACK
   ▼
[프론트] 성공 메시지 + 상품 목록 다시 불러오기 (재고 갱신)
```
